# Audit et corrections — 17 octobre 2026

Analyse du code local de KAOBASE, des migrations et des tests. L'arbre Git était propre au début de cette intervention. Les changements du présent diff appartiennent à cette intervention ; aucun commit, déploiement ou changement de base distante n'a été effectué.

## Problèmes corrigés

| Priorité | Faiblesse constatée | Correction et vérification |
|---|---|---|
| P1 | La confirmation IA autorisait une suppression dès qu'un message contenait « OK » ou « je confirme », sans lier cet accord à une cible. Le retrait d'un budget n'avait pas ce garde. | Les outils ne suppriment plus : ils préparent une demande liée à un utilisateur, une conversation, un type et une cible. Le clic utilisateur appelle une route distincte ; la suppression et son reçu sont atomiques. Expiration, contrôle d'espace, comparaison d'aperçu, verrouillage et usage unique sont vérifiés en SQL. Les boutons anciens sont invalidés si un autre onglet renouvelle un aperçu modifié. Tests SQL réels, outils et route HTTP. |
| P1 | La RLS contrôlait le propriétaire de chaque ligne, mais les clés étrangères simples autorisaient une référence vers l'objet d'un autre utilisateur si son UUID était connu. Aucune lecture directe des données de l'autre utilisateur n'a été démontrée. | Douze clés étrangères composites imposent le même `user_id` côté enfant et parent, en conservant les relations PostgREST et les comportements `SET NULL`/`CASCADE`. Le précontrôle bloque atomiquement la migration si des références existantes sont invalides. 43 tests PostgreSQL vérifient insertions, mises à jour, suppressions et préservation des données. |
| P1 | Les requêtes IA simultanées pouvaient toutes passer le comptage avant l'enregistrement des messages. Une erreur de lecture laissait également passer l'appel. | Réservation en base avant l'appel IA, sérialisée par utilisateur, sur une table non modifiable par le client. Quotas conservés : 6/minute et 150/24 h. Si le contrôle échoue, réponse 503 sans appel IA. Les compteurs de l'interface utilisent les réservations. |
| P1 | Le repli IA pouvait rejouer les outils d'une conversation après un échec du fournisseur survenu après une écriture. | Le repli reste disponible avant toute exécution d'outil ; après démarrage d'un outil, l'erreur est propagée sans rejouer la conversation sur un autre modèle. Six tests avec fournisseurs simulés couvrent erreurs avant/après écriture et résultats asynchrones. |
| P1 | Les abonnements d'un même marchand étaient fusionnés entre perso/pro ; la redétection pouvait écraser les choix manuels. | Identité `(user_id, space, merchant)`, détection et rejets séparés par espace. Seules les nouvelles suggestions jamais modifiées restent gérées automatiquement ; une modification utilisateur les protège, y compris en concurrence avec une redétection. Erreurs DB propagées et compteurs basés sur les lignes écrites. |
| P1 | Un OFX multi-comptes était aplati dans le compte cible unique de l'interface. Des montants/dates ou colonnes CSV ambigus pouvaient produire des opérations erronées. | Rejet global explicite des OFX contenant plusieurs relevés/comptes ; validation des colonnes et mappings CSV ; rejet des lignes décalées, montants ambigus, formats hexadécimaux/exponentiels, précisions supérieures au centime et champs débit/crédit contradictoires. Dates validées sur le calendrier réel. L'action d'import transmet l'erreur précise avant toute écriture. |
| P2 | Les échéances de fin de mois dérivaient après février, et l'ancre était perdue entre affichage et prévision. | Jour contractuel persisté dans `anchor_day`, transmis jusqu'aux prévisions. Tests mensuels, trimestriels, bissextiles et base→affichage→prévision. Les formulaires qui renvoient la date déjà avancée conservent le jour contractuel. |
| P2 | Le chat annonçait une action effectuée à partir du nom de l'outil, même si son résultat était un refus. Certaines erreurs techniques étaient renvoyées telles quelles. | Badges issus des résultats réussis ; demandes de confirmation et erreurs exclues. Traduction des erreurs techniques côté agents et feedback. |
| Local | Le build Turbopack échouait en ouvrant son cache persistant ; ce cache contenait des fichiers dupliqués dans le dossier Documents. | Le seul cache `.next/cache/turbopack` a été déplacé dans la Corbeille avec `trash`. Le build standard a ensuite compilé. Aucun fichier source supprimé. |

## Vérification

Les tests SQL exécutent les migrations réelles sur PostgreSQL via PGlite et pgvector, sans credentials ni service distant. Les tests d'outils, fournisseurs et routes HTTP utilisent des doubles locaux.

| Vérification finale | Résultat |
|---|---|
| `npm test` | 212 tests réussis dans 13 fichiers |
| `npm run typecheck` | Réussi |
| `npm run lint` | Réussi |
| `npm run build` | Réussi avec Turbopack |
| `E2E_BASE_URL=http://localhost:3201 npm run test:e2e -- --project=public` | 5 tests publics réussis, dont refus de l'API de confirmation sans session |
| `git diff --check` | Réussi |
| `npm audit --omit=dev` | 0 vulnérabilité |

Les serveurs locaux lancés pour ces contrôles ont été arrêtés. Les deux dépendances PGlite ajoutées sont réservées au développement ; aucun moteur de base supplémentaire n'entre dans le bundle de production.

Les tests PGlite sérialisent les requêtes au sein d'une même instance : ils vérifient les seuils, les fenêtres et les droits, mais ne constituent pas un test de charge avec plusieurs connexions PostgreSQL réelles. Le verrou transactionnel de réservation est présent dans la fonction SQL.

## Mise en service

Appliquer les quatre nouvelles migrations dans l'ordre puis déployer le code correspondant :

1. `supabase/migrations/20261017010000_ownership_integrity.sql`
2. `supabase/migrations/20261017020000_subscription_identity.sql`
3. `supabase/migrations/20261017030000_agent_deletion_requests.sql`
4. `supabase/migrations/20261017040000_agent_request_limits.sql`

La première migration ne détache ni n'efface de référence invalide : elle signale les colonnes concernées et annule sa transaction. Une telle donnée doit être examinée avant de relancer la migration. Les colonnes nouvelles sont requises par le code des abonnements ; les migrations de quota et de confirmation sont requises pour activer ces parcours. Elles n'ont pas été appliquées à Supabase distant pendant cette intervention.

## Limites et points restant à traiter

- Aucun test connecté au compte utilisateur, appel réel Groq/Gemini, envoi d'email, déploiement Vercel ou inspection de la configuration distante Supabase n'a été effectué. Les cinq tests E2E publics utilisent le serveur local.
- L'identité des abonnements distingue désormais perso/pro ; plusieurs contrats du même marchand dans un même espace restent agrégés. Un identifiant de contrat ou un lien de compte serait nécessaire pour affiner cette distinction.
- Le jour contractuel déjà perdu dans des données historiques ne peut pas être restauré avec certitude. Les abonnements existants restent sous contrôle utilisateur par prudence.
- Les OFX comportant plusieurs relevés, même pour le même compte, sont refusés par prudence. La devise source OFX n'est pas comparée à celle du compte cible ; aucune conversion monétaire n'a été ajoutée.
- Les limites historiques de volume des requêtes financières et de détection restent présentes ; ce travail ne certifie pas l'exactitude sur un historique dépassant les plafonds configurés.
- La configuration SMTP et les fonctions d'export/suppression de compte restent dans `TODOS.md`. Ce sont des travaux distincts des corrections réalisées ici.
- `npm audit --omit=dev` ne signale aucune vulnérabilité. L'audit complet signale cinq entrées dans la chaîne de développement ESLint correspondant à une seule vulnérabilité transitive de `braces`. L'[avis GitHub GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) n'annonce pas de version corrigée à la date de cet audit. Aucun downgrade cassant de Next.js ni override non validé n'a été introduit.

L'[audit séparé des compétences](skills-audit-2026-10-17.md) inventorie les 19 compétences du périmètre du script, sa couverture historique et cinq écarts de contrôles d'invocation. Aucune compétence globale n'a été modifiée.
